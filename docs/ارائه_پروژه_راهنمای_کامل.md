## ۱. پروژه در یک نگاه

**این پروژه چه می‌کند؟**
یک سیستم **حضور و غیاب خودکار** است که به‌جای انگشت‌زنی یا کارت، از **چهره‌ی افراد** استفاده می‌کند. یک دوربین (وب‌کم) تصویر زنده می‌گیرد، سیستم چهره‌ها را پیدا می‌کند، تشخیص می‌دهد این چهره متعلق به کدام کارمند ثبت‌شده است، و ساعت **ورود (اولین دیده‌شدن)** و **خروج (آخرین دیده‌شدن)** او را در یک دیتابیس ذخیره می‌کند. یک صفحه‌ی وب (داشبورد) هم تصویر زنده و گزارش حضور را نشان می‌دهد.

**ورودی و خروجی سیستم:**
- **ورودی:** فریم‌های ویدیویی زنده از دوربین.
- **خروجی:** جدول حضور روزانه (چه کسی، از ساعت چند تا چند، چند ساعت کار کرد) + خروجی CSV (فایل اکسل‌مانند).

**سه بخش اصلی:**
1. **موتور تشخیص چهره** (بینایی ماشین + هوش مصنوعی) — فایل [face_recognizer.py](file:///s:/TRAE/CV_Attendance/face_recognizer.py)
2. **داده و منطق حضور** (دیتابیس + محاسبه‌ی ساعت کار) — پوشه‌ی [models/](file:///s:/TRAE/CV_Attendance/models) و [attendance.py](file:///s:/TRAE/CV_Attendance/attendance.py)
3. **وب و API** (داشبورد، پنل ادمین، امنیت) — [main_fastapi.py](file:///s:/TRAE/CV_Attendance/main_fastapi.py) و [auth.py](file:///s:/TRAE/CV_Attendance/auth.py)

## ۲. واژه‌نامه

این جدول را قبل از ارائه بخوان. اگر داور بپرسد «فلان کلمه یعنی چه؟» باید بلد باشی.

| اصطلاح | تلفظ / معنی ساده | توضیح |
|---|---|---|
| **CV (Computer Vision)** | بینایی ماشین | علمی که به کامپیوتر یاد می‌دهد از روی تصویر «بفهمد» چه چیزی می‌بیند. |
| **Frame (فریم)** | قاب / تصویر لحظه‌ای | ویدیو در واقع تعداد زیادی عکس پشت سر هم است. هر عکس یک «فریم» است. مثلاً ۳۰ فریم در ثانیه. |
| **Face Detection (آشکارسازی چهره)** | «کجا چهره هست؟» | فقط پیدا می‌کند در تصویر چهره کجاست (یک کادر دور صورت). هنوز نمی‌داند چه کسی است. |
| **Face Recognition (شناسایی چهره)** | «این چهره‌ی کیست؟» | بعد از پیدا کردن چهره، تشخیص می‌دهد متعلق به کدام فرد ثبت‌شده است. |
| **Embedding (بردار چهره / امبدینگ)** | «امضای عددی صورت» | مهم‌ترین مفهوم پروژه. یک لیست از اعداد (بردار) که هویت ریاضیِ یک صورت است. توضیح کامل در بخش ۵. |
| **Vector (بردار)** | لیستی از اعداد | مثل `[0.12, -0.98, 0.33, ...]`. در این پروژه ۵۱۲ عدد. |
| **512-dim (۵۱۲ بُعدی)** | بردار با ۵۱۲ عدد | یعنی امضای هر صورت دقیقاً ۵۱۲ عدد است. هرچه بردار بلندتر، توصیف صورت دقیق‌تر. |
| **InsightFace** | نام یک کتابخانه | یک ابزار آماده و قوی برای چهره که هم چهره را پیدا می‌کند و هم بردار می‌سازد. |
| **ArcFace** | نام مدل هوش مصنوعی | مدلی که تصویر صورت را به بردار ۵۱۲ عددی تبدیل می‌کند (داخل InsightFace). |
| **RetinaFace / SCRFD** | آشکارساز چهره | مدلی که چهره‌ها را در تصویر پیدا می‌کند (داخل InsightFace). SCRFD نسخه‌ی سریع‌تر آن است. |
| **dlib / face_recognition** | کتابخانه‌ی جایگزین | یک روش قدیمی‌تر که بردار ۱۲۸ عددی می‌سازد. در این پروژه فقط «پشتیبان» است اگر InsightFace کار نکند. |
| **buffalo_l** | نام بسته‌ی مدل | مجموعه مدل آماده‌ی InsightFace که پروژه استفاده می‌کند. |
| **Cosine Similarity (شباهت کسینوسی)** | معیار شباهت دو بردار | عددی بین ۱- تا ۱. هرچه به ۱ نزدیک‌تر، دو صورت شبیه‌ترند. توضیح در بخش ۵. |
| **Euclidean Distance (فاصله اقلیدسی)** | فاصله‌ی مستقیم دو نقطه | همان فاصله‌ی معمولی؛ در روش dlib برای مقایسه استفاده می‌شود. |
| **Tolerance (آستانه تحمل)** | حد مجاز تفاوت | تعیین می‌کند چقدر تفاوت را «همان آدم» حساب کنیم. در پروژه ۰٫۶٪. |
| **Pipeline (خط لوله)** | زنجیره‌ی مراحل | یعنی داده از مرحله‌ای به مرحله‌ی بعد می‌رود: دوربین → تشخیص → مقایسه → ثبت. |
| **Landmark (نقاط کلیدی چهره)** | چشم، بینی، دهان و... | مختصات نقاط مهم صورت. برای هم‌ترازی و تشخیص زنده‌بودن. |
| **Alignment (هم‌ترازی)** | صاف کردن صورت | چرخاندن صورت کج تا صاف شود، چون مدل روی صورت صاف بهتر کار می‌کند. |
| **Liveness (زنده‌بودن)** | «آدم واقعی است یا عکس؟» | جلوگیری از تقلب؛ اگر کسی عکس چاپی یا موبایل جلوی دوربین بگیرد باید رد شود. |
| **Tracking (ردیابی)** | دنبال کردن چهره بین فریم‌ها | یک صورت را بین فریم‌های پشت سر هم دنبال می‌کند تا تشخیص پایدارتر شود. |
| **Quality Assessment (ارزیابی کیفیت)** | «تصویر خوب است؟» | چک می‌کند صورت تار، تاریک یا خیلی کج نباشد. |
| **Database / DB (دیتابیس)** | پایگاه داده | جایی که اطلاعات (کارمندان، بردارها، حضور) ذخیره می‌شود. |
| **SQLite** | نوع دیتابیس | یک دیتابیس ساده که در یک فایل ذخیره می‌شود: `cv_attendance.db`. |
| **ORM** | نگاشت شیء-رابطه‌ای | ابزاری که اجازه می‌دهد به‌جای دستورات پیچیده‌ی دیتابیس، با کلاس‌های پایتون کار کنیم. اینجا SQLAlchemy. |
| **SQLAlchemy** | کتابخانه‌ی ORM | همان ابزار ORM پروژه. |
| **Migration (مایگریشن)** | تغییر ساختار دیتابیس | وقتی جدول جدید یا ستون جدید لازم داریم، مایگریشن ساختار را به‌روز می‌کند. ابزارش Alembic است. |
| **API** | رابط برنامه‌نویسی | مجموعه‌ای از «آدرس»ها (مثل `/workers`) که برنامه‌ی دیگر می‌تواند صدا بزند تا کاری انجام شود. |
| **FastAPI** | فریم‌ورک وب | ابزار ساخت API و سرور وب با پایتون. سریع و مدرن. |
| **Endpoint (اندپوینت)** | یک آدرس API | مثلاً `/api/dashboard` یک اندپوینت است. |
| **MJPEG** | نوع پخش ویدیو | روشی برای پخش زنده‌ی ویدیو در مرورگر با فرستادن پشت‌سرهم عکس‌های JPEG. |
| **Event Loop (حلقه رویداد)** | مدیر کارها در FastAPI | بخشی که درخواست‌ها را نوبتی مدیریت می‌کند. اگر یک کار سنگین آن را «قفل» کند، همه کند می‌شوند. |
| **Thread / Thread Pool (نخ / استخر نخ)** | اجرای موازی کارها | نخ یعنی یک خط اجرای مستقل. کار سنگین را به نخ جدا می‌سپاریم تا سرور کند نشود. |
| **JWT** | توکن امنیتی | یک «بلیت» رمزنگاری‌شده که ثابت می‌کند کاربر کیست، بدون اینکه هر بار رمز بفرستد. |
| **RBAC** | کنترل دسترسی نقش‌محور | هر کاربر یک «نقش» دارد (ادمین، مدیر، ...) و هر نقش اجازه‌های مشخصی دارد. |
| **Guest (مهمان)** | چهره‌ی ناشناس | صورتی که دیده شده ولی ثبت‌نشده است. حضورش ثبت نمی‌شود تا کسی او را «کارمند» کند. |
| **Augmentation (تقویت نمونه)** | ذخیره‌ی نمونه‌های بیشتر | وقتی فرد کمی متفاوت دیده می‌شود (زاویه/نور دیگر)، بردار جدیدش ذخیره می‌شود تا تشخیص بهتر شود. |

## ۳. پیش‌زمینه‌های لازم

قبل از اینکه وارد کد شویم، این چهار مفهوم پایه را باید بفهمی. اینها ستون فقرات کل پروژه‌اند.

### ۳٫۱. تصویر برای کامپیوتر یعنی «عدد»
کامپیوتر عکس را نمی‌بیند؛ عکس برای او یک **جدول از اعداد** است. هر نقطه‌ی تصویر (پیکسل) سه عدد دارد: میزان قرمز، سبز و آبی (RGB) بین ۰ تا ۲۵۵. پس یک تصویر رنگی ۶۴۰×۴۸۰ در واقع یک آرایه‌ی سه‌بعدی از اعداد است. کتابخانه‌ای که این آرایه‌ها را مدیریت می‌کند **NumPy** نام دارد و کتابخانه‌ای که کار تصویری انجام می‌دهد **OpenCV (cv2)** است.

> نکته‌ی مهم برای ارائه: OpenCV رنگ‌ها را به ترتیب **BGR** (آبی-سبز-قرمز) نگه می‌دارد، نه RGB. برای همین در کد جاهایی `cvtColor(..., COLOR_BGR2RGB)` می‌بینی؛ یعنی تبدیل ترتیب رنگ.

### ۳٫۲. بردار (Vector) و «شباهت»
بردار یعنی یک لیست از اعداد، مثلاً `[۰٫۱، -۰٫۹، ۰٫۳]`. هر بردار را می‌توان یک «نقطه» یا «جهت» در فضا تصور کرد. ایده‌ی کلیدی پروژه این است:

> اگر بتوانیم هر صورت را به یک بردار تبدیل کنیم، آن‌گاه **صورت‌های شبیه، بردارهای نزدیک** خواهند داشت. پس «تشخیص چهره» تبدیل می‌شود به «مقایسه‌ی دو بردار».

### ۳٫۳. مدل هوش مصنوعی (شبکه عصبی)
یک **مدل** (اینجا ArcFace) برنامه‌ای است که قبلاً روی میلیون‌ها عکس صورت «آموزش دیده». کار آن این است: تصویر یک صورت را بگیرد و بردار ۵۱۲ عددی آن را بدهد. ما این مدل را آموزش نداده‌ایم؛ آن را **آماده (pre-trained)** استفاده می‌کنیم. مدل به فرمت **ONNX** ذخیره شده و با **ONNX Runtime** اجرا می‌شود (موتوری که مدل‌های آماده را روی CPU/GPU اجرا می‌کند).

### ۳٫۴. سرور، دیتابیس و API
- **سرور:** برنامه‌ای که همیشه روشن است و به درخواست‌های مرورگر پاسخ می‌دهد.
- **دیتابیس:** انبار داده‌ی ماندگار (حتی بعد از خاموش شدن برنامه باقی می‌ماند).
- **API:** پل ارتباطی؛ مرورگر با فرستادن درخواست به آدرس‌هایی مثل `/api/dashboard`، داده می‌گیرد.

## ۴. معماری کلی سیستم

مسیر کلی داده در سیستم («خط لوله» یا Pipeline) به این شکل است:

```
دوربین (وب‌کم)
   │  فریم خام (raw_frame)
   ▼
آشکارسازی چهره (RetinaFace/SCRFD)  ← کجا چهره هست؟
   │  کادر دور هر صورت + نقاط کلیدی
   ▼
ارزیابی کیفیت (Quality)  ← تار/تاریک نباشد
   │
   ▼
ساخت بردار ۵۱۲ عددی (ArcFace) ← امضای عددی صورت
   │
   ▼
مقایسه با دیتابیس (شباهت کسینوسی) ← این کیست؟
   │
   ▼
تشخیص زنده‌بودن (Liveness) ← عکس نباشد
   │
   ▼
ردیابی چهره (Tracking) ← تثبیت هویت بین فریم‌ها
   │
   ▼
ثبت حضور (Attendance) → دیتابیس → داشبورد وب
```

این توضیح دقیقاً در بالای فایل [face_recognizer.py](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L9-L11) به‌صورت کامنت نوشته شده است:

```python
Pipeline:
  Frame → RetinaFace detect → Quality gate → ArcFace encode →
  Match DB → Liveness check → Kalman tracking → Augmentation
```

**سه لایه‌ی نرم‌افزار:**
1. **لایه‌ی بینایی:** فایل‌های `face_recognizer.py` و پوشه‌ی `cv_modules/`.
2. **لایه‌ی داده:** پوشه‌ی `models/` و `attendance.py`.
3. **لایه‌ی وب:** `main_fastapi.py`، `auth.py` و پوشه‌ی `templates/`.

## ۵. قلب پروژه: بردار چهره

این بخش دقیقاً جوابِ سوال توست: «وقتی می‌گویی از صورت بردار ریاضی برمی‌دارد، دقیقاً چطور، کِی، چه می‌کند، کجا ذخیره می‌شود و چطور مقایسه می‌شود؟» این را با جزئیات و کد واقعی توضیح می‌دهم.

### ۵٫۱. «برداشتن بردار» دقیقاً یعنی چه؟
منظور از «بردار برداشتن از صورت» این است: تصویرِ کوچکِ صورت را به مدل ArcFace می‌دهیم، و مدل یک آرایه‌ی ۵۱۲ عددی برمی‌گرداند. این ۵۱۲ عدد، **امضای یکتای آن صورت** است. صورت‌های یک نفر، امضاهای نزدیک به هم دارند؛ صورت‌های دو نفر متفاوت، امضاهای دور از هم.

این عدد ۵۱۲ در تعریف کلاس، در کامنت کد آمده است — [face_recognizer.py](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L57-L61):

```python
Key improvements over v1:
  - RetinaFace detection (more robust than HOG)
  - ArcFace encoding (512-dim, higher accuracy than dlib 128-dim)
```

### ۵٫۲. کِی و کجا بردار ساخته می‌شود؟
مدل InsightFace هنگام راه‌اندازی برنامه یک بار بارگذاری می‌شود. این کار در سازنده‌ی کلاس `FaceRecognizer` انجام می‌شود — [face_recognizer.py](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L119-L139):

```python
from insightface.app import FaceAnalysis as InsightFaceAnalysis
self._insightface_app = InsightFaceAnalysis(
    name="buffalo_l",
    providers=["CPUExecutionProvider"],
    allowed_modules=["detection", "recognition"],
)
det = int(insightface_det_size)
self._insightface_app.prepare(ctx_id=-1, det_size=(det, det))
```

توضیح خط به خط:
- `name="buffalo_l"`: کدام بسته‌ی مدل استفاده شود.
- `providers=["CPUExecutionProvider"]`: مدل روی **پردازنده (CPU)** اجرا شود، نه کارت گرافیک.
- `allowed_modules=["detection", "recognition"]`: فقط دو کار لازم را روشن کن: پیدا کردن چهره و ساختن بردار. (ماژول‌های اضافی مثل تشخیص سن/جنسیت خاموش شده‌اند تا سرعت بالا برود — همان‌طور که در کامنت [خط ۱۲۵-۱۲۷](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L125-L127) گفته سرعت هر فریم را از ~۷۴۰ms به ~۶۲۵ms رساند.)
- `det_size=(det, det)`: اندازه‌ای که تصویر برای آشکارسازی به آن تغییر می‌کند. **باید مربع باشد** (مثلاً ۳۲۰×۳۲۰).

> **این همان باگِ معروف پروژه است (SCRFD broadcast).** اگر اندازه مربع نباشد (مثلاً ۳۲۰×۲۴۰)، آشکارساز SCRFD خطای «broadcast» می‌دهد چون شبکه‌ی نقاط لنگر (anchor) را از ارتفاع می‌سازد و برای هر دو محور به کار می‌برد. کامنت این موضوع دقیقاً در [خط ۱۳۰-۱۳۴](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L130-L134) توضیح داده شده:
>
> ```python
> # det_size must be square: SCRFD builds its anchor grid from the
> # input height for both axes, so a non-square size such as
> # (320, 240) raises "operands could not be broadcast together
> # with shapes (140,) (160,)" inside distance2bbox().
> ```
>
> راه‌حل: پارامتر به `det_size=(320, 320)` اصلاح شد. (این کار حامد نبی‌پور است — بخش ۱۰.)

### ۵٫۳. مرحله‌ی ساخت بردار در عمل
تابع اصلی که هر فریم را پردازش می‌کند `recognize` است، که کار را به `_recognize_insightface` می‌سپارد. در آن‌جا با یک فراخوانی، هم چهره‌ها پیدا می‌شوند و هم بردارشان ساخته می‌شود — [face_recognizer.py](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L242):

```python

```

سپس برای هر چهره‌ی پیداشده، بردار آماده است و فقط از آن خوانده می‌شود — [خط ۲۸۰-۲۸۷](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L280-L287):

```python

    continue

# Normalize encoding for cosine similarity
```

توضیح:

### ۵٫۵. چطور مقایسه می‌شود؟ (شناسایی زنده)
حالا فرد جلوی دوربین است. بردار او ساخته می‌شود و باید با همه‌ی بردارهای ذخیره‌شده مقایسه شود تا نزدیک‌ترین پیدا شود. این مقایسه با **شباهت کسینوسی** انجام می‌شود.

اول، بردارهای ذخیره‌شده از دیتابیس خوانده و یک‌بار نرمال می‌شوند تا ماتریس مقایسه ساخته شود — [face_recognizer.py](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L331-L345):

```python
if known_matrix is None:
    dim = encoding_norm.shape[0]
    filtered = [
        (kid, np.asarray(ke, dtype=np.float32))
        for kid, ke in zip(known_ids, known_encs)
        if np.asarray(ke).shape[0] == dim
    ]
    ...
    known_matrix = np.array([
        e / (np.linalg.norm(e) + 1e-8) for _, e in filtered
    ])
```

> نکته‌ی مهم: شرط `if np.asarray(ke).shape[0] == dim` فقط بردارهای **هم‌بُعد** را نگه می‌دارد. چون دیتابیس ممکن است هم بردار ۵۱۲ عددی (ArcFace) و هم ۱۲۸ عددی (dlib قدیمی) داشته باشد، و مقایسه‌ی بردار ۵۱۲ با ۱۲۸ بی‌معنی است و خطا می‌دهد.

سپس مقایسه‌ی واقعی — [خط ۳۴۷-۳۵۶](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L347-L356):

```python
if known_matrix.shape[0] > 0:
    similarities = known_matrix @ encoding_norm  # cosine similarity
    best_idx = int(np.argmax(similarities))
    best_sim = float(similarities[best_idx])

    arcface_min_sim = 1.0 - self.tolerance
    if best_sim > arcface_min_sim:
        person_id = match_ids[best_idx]
```

توضیح دقیق:
- `known_matrix @ encoding_norm`: علامت `@` یعنی **ضرب ماتریسی**. چون همه‌ی بردارها نرمال شده‌اند، حاصلِ ضرب هر بردار ذخیره‌شده در بردار زنده، همان **شباهت کسینوسی** آن دو است. نتیجه یک لیست از شباهت‌هاست (برای هر بردار ذخیره‌شده یک عدد).
- `np.argmax(similarities)`: اندیسِ بیشترین شباهت را می‌دهد؛ یعنی نزدیک‌ترین فرد.
- `best_sim`: مقدار آن بیشترین شباهت.
- `arcface_min_sim = 1.0 - self.tolerance`: آستانه. `tolerance` پیش‌فرض ۰٫۶ است، پس آستانه ۰٫۴ می‌شود. یعنی اگر شباهت **بیشتر از ۰٫۴** باشد، همان فرد است.
- اگر شرط برقرار باشد، `person_id` تنظیم می‌شود؛ یعنی «این کارمند شناخته شد».

**اطمینان (Confidence):** فقط شناسایی کافی نیست؛ سیستم یک درصد اطمینان هم حساب می‌کند تا اگر نفر دوم هم تقریباً به همان اندازه شبیه بود، اطمینان پایین بیاید — [خط ۳۶۲-۳۷۱](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L362-L371):

```python
if similarities.shape[0] >= 2:
    sd = np.sort(similarities)[::-1]  # descending
    margin = float(sd[0] - sd[1])
    confidence = best_sim * min(1.0, 0.5 + margin)
else:
    confidence = best_sim
confidence = max(0.0, min(1.0, confidence))
confidence = confidence * (0.5 + 0.5 * quality_score)
```

- `margin = sd[0] - sd[1]`: فاصله‌ی بهترین شباهت با دومی. اگر این فاصله کم باشد، یعنی سیستم مطمئن نیست، پس اطمینان کم می‌شود.
- خط آخر اطمینان را در **کیفیت تصویر** ضرب می‌کند؛ تصویر بی‌کیفیت، اطمینان کمتر.

### ۵٫۶. تفاوت روش ذخیره‌سازی و شناسایی — نکته‌ی مهم مصاحبه
یک تصمیم فنی مهم: **هم‌ترازی (align) دستیِ اضافه حذف شده** و برای ثبت‌نام و شناسایی از یک مسیر یکسان استفاده می‌شود. دلیلش این است که ArcFace خودش داخل مدل، صورت را از روی ۵ نقطه‌ی کلیدی صاف و به اندازه‌ی ۱۱۲×۱۱۲ می‌برد؛ اگر ما دوباره دستی صاف کنیم و کدگذاری کنیم، فقط بین بردارهای یک نفر «نویز» اضافه می‌شود. این دقیقاً در کامنت کد آمده — [خط ۲۹۲-۲۹۶](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L292-L296):

```python

# 112x112 from the 5-point landmarks, so re-encoding our aligned
```

> **جمع‌بندی بخش ۵ (برای اسلاید):**
> ۱. **چطور؟** مدل ArcFace تصویر صورت را می‌گیرد و بردار ۵۱۲ عددی می‌سازد.
> ۲. **کِی؟** هنگام ثبت‌نام (برای ذخیره) و در هر فریم زنده (برای شناسایی).
> ۳. **چه می‌کند؟** بردار را نرمال می‌کند تا آماده‌ی مقایسه شود.

> ۵. **چطور مقایسه می‌شود؟** با شباهت کسینوسی (ضرب ماتریسی بردارهای نرمال‌شده) و آستانه‌ی ۰٫۴.

### ۶٫۱. خواندن فریم از دوربین
یک **نخ (Thread) پس‌زمینه** مدام از دوربین فریم می‌خواند. این حلقه `camera_loop` است — [main_fastapi.py](file:///s:/TRAE/CV_Attendance/main_fastapi.py#L353-L371):

نکته‌ی کلیدی و تصمیم مهندسی مهم: **دو نوع فریم داریم**:

> ```

### ۶٫۲. پردازش نتایج و ثبت حضور
بعد از شناسایی، تابع `_process_results` تصمیم می‌گیرد چه کاری انجام شود — [main_fastapi.py](file:///s:/TRAE/CV_Attendance/main_fastapi.py#L443-L481):

```python
for r in results:

    # Unknown face
    if pid is None:
        ...  # نگه‌داشتن برای ثبت به‌عنوان مهمان
        continue

    # Guests are recognized but have no attendance record...
    if not pid.startswith("W"):
        continue

        continue

```

توضیح منطق:
- اگر `person_id` تهی باشد، چهره **ناشناس** است → کاندید ثبت به‌عنوان مهمان.
- اگر شناسه با `W` شروع نشود (یعنی مهمان است، نه کارمند `W001`)، حضورش ثبت **نمی‌شود**. این جلوی «حضور کاذب» را می‌گیرد.
- **Cooldown (زمان خنک‌شدن):** اگر یک نفر را همین چند ثانیه پیش ثبت کردیم، دوباره ثبت نمی‌کنیم تا دیتابیس پر از رکورد تکراری نشود (پیش‌فرض ۸ ثانیه).
- در نهایت `record_sighting` را صدا می‌زند که حضور را ثبت می‌کند.

### ۶٫۳. منطق «ورود» و «خروج»
این پروژه سبک ساده و هوشمندی برای حضور دارد: **اولین بار دیده‌شدن = ورود، آخرین بار دیده‌شدن = خروج**. توضیحش در بالای [attendance.py](file:///s:/TRAE/CV_Attendance/attendance.py#L1-L8) آمده:

```python
A worker's "clock-in" is the first time their face is seen in a day and
"clock-out" is the last time it is seen. ... Working hours are simply
`last_seen - first_seen`.
```

و در تابع `record_sighting` این‌طور اجرا می‌شود — [attendance.py](file:///s:/TRAE/CV_Attendance/attendance.py#L109-L119):

```python
if sighting is None:
    sighting = FaceSighting(
        worker_id=worker.id,
        event_date=now,
        first_seen=now,
        last_seen=now,
    )
    db.add(sighting)
else:
    sighting.last_seen = now
db.commit()
```

- **بار اول در روز:** یک رکورد `FaceSighting` ساخته می‌شود با `first_seen = last_seen = الان`.
- **دفعات بعد:** فقط `last_seen` به‌روز می‌شود.
- **ساعت کار** = `last_seen - first_seen`.

### ۷٫۲. سازگاری با دو نوع دیتابیس
یک نکته‌ی مهندسی: پروژه با **SQLite** (ساده، فایلی) و **PostgreSQL** (قوی، سروری) هر دو کار می‌کند. برای شناسه‌ها یک نوع سفارشی `GUID` ساخته شده که خودش تشخیص می‌دهد روی کدام دیتابیس است — [base.py](file:///s:/TRAE/CV_Attendance/models/base.py#L16-L27):

```python
    def load_dialect_impl(self, dialect):
        if dialect.name == "postgresql":
            return dialect.type_descriptor(PG_UUID(as_uuid=True))
        else:
            return dialect.type_descriptor(CHAR(36))
```

### ۷٫۳. Repository — لایه‌ی واسط دیتابیس
همه‌ی کارهای دیتابیس (افزودن کارمند، خواندن بردارها، حذف و...) در یک کلاس به‌نام `FaceRepository` جمع شده‌اند — [repository.py](file:///s:/TRAE/CV_Attendance/models/repository.py). این کار خوبی است چون بقیه‌ی برنامه نیازی ندارد جزئیات دیتابیس را بداند؛ فقط متدهای ساده مثل `get_all_known()` یا `add_worker()` را صدا می‌زند.

تابع مهم `get_all_known` همه‌ی بردارهای کارمندان فعال و مهمان‌ها را برای مقایسه برمی‌گرداند — [repository.py](file:///s:/TRAE/CV_Attendance/models/repository.py#L69-L90).

### ۷٫۴. کَش (Cache) برای سرعت
اگر برای هر فریم به دیتابیس می‌زدیم، خیلی کند می‌شد. برای همین بردارهای شناخته‌شده در حافظه **کَش (Cache = ذخیره‌ی موقت سریع)** می‌شوند و هر ۵ ثانیه یک‌بار تازه می‌شوند — [face_recognizer.py](file:///s:/TRAE/CV_Attendance/face_recognizer.py#L225-L231):

```python
def _get_known(self) -> tuple[List[str], List[np.ndarray]]:
    """Known encodings, cached for a short TTL to keep the loop off the DB."""
    now = time.time()
    if self._known_cache is None or now - self._known_cache_at > self._known_cache_ttl:
        self._known_cache = self.db.get_all_known()
        self._known_cache_at = now
    return self._known_cache
```

- `TTL (Time To Live)`: مدت‌زمانی که کَش معتبر است (اینجا ۵ ثانیه).
- وقتی کارمندی اضافه/حذف می‌شود، `invalidate_cache()` صدا زده می‌شود تا کَش دور ریخته و تازه شود.

### ۸٫۱. FastAPI و مشکل «قفل شدن سرور»
سرور با **FastAPI** ساخته شده. FastAPI یک **Event Loop (حلقه‌ی رویداد)** دارد که درخواست‌ها را نوبتی مدیریت می‌کند. مشکل این بود: کارهای دیتابیسی **مسدودکننده (blocking)** هستند و اگر مستقیم در حلقه اجرا شوند، کل سرور تا پایان آن کار «قفل» می‌شود و مرورگر تایم‌اوت می‌دهد.

**راه‌حل:** اندپوینت‌هایی که کار دیتابیسی سنگین دارند به‌جای `async def` به‌صورت `def` معمولی تعریف شده‌اند. وقتی FastAPI یک تابع معمولی می‌بیند، آن را در یک **Thread Pool (استخر نخ)** جدا اجرا می‌کند و حلقه‌ی اصلی آزاد می‌ماند. توضیحش در کامنت کد آمده — [main_fastapi.py](file:///s:/TRAE/CV_Attendance/main_fastapi.py#L1205-L1212):

```python
@app.get("/api/dashboard", tags=["Dashboard"])
def api_dashboard():
    """JSON dashboard data.

    Declared sync on purpose: every call does blocking DB work, so Starlette
    runs it in the threadpool instead of stalling the event loop (which made the
    browser's 5s fetch timeout abort while the camera thread held the GIL).
    """
```

> این همان بهینه‌سازی هم‌روندی است که زمان پاسخ API را به ۵۵ تا ۸۹ میلی‌ثانیه رساند. کار امیرمحمد احمدی — بخش ۱۰.
>
> **GIL** که در کامنت آمده یعنی «قفل سراسری مفسر پایتون»؛ محدودیتی که باعث می‌شود در یک لحظه فقط یک نخ کد پایتون اجرا کند. به همین دلیل مدیریت درست نخ‌ها حیاتی است.

### ۸٫۴. امنیت: JWT و RBAC
دو سازوکار امنیتی داریم:

**۱) JWT (توکن):** وقتی کاربر با نام و رمز وارد می‌شود، سرور یک «بلیت» رمزنگاری‌شده به او می‌دهد. کاربر این بلیت را در درخواست‌های بعدی می‌فرستد و دیگر لازم نیست هر بار رمز بدهد — [auth.py](file:///s:/TRAE/CV_Attendance/auth.py#L109-L123):

```python
def create_access_token(data: dict, expires_delta: Optional[timedelta] = None) -> str:
    to_encode = data.copy()
    ...
    to_encode.update({"exp": expire, "iat": now, "type": "access"})
    encoded_jwt = jwt.encode(to_encode, settings.secret_key, algorithm=settings.algorithm)
    return encoded_jwt
```

- `exp`: زمان انقضای توکن (پیش‌فرض ۳۰ دقیقه). بعد از آن باید تازه شود.
- توکن با یک **کلید مخفی (secret_key)** امضا می‌شود؛ کسی نمی‌تواند توکن جعلی بسازد.

**۲) RBAC (کنترل دسترسی نقش‌محور):** هر کاربر یک **نقش** دارد و هر نقش مجموعه‌ای از **اجازه‌ها** — [auth.py](file:///s:/TRAE/CV_Attendance/auth.py#L50-L84):

```python
ROLE_PERMISSIONS = {
    Role.ADMIN: [ ... همه‌ی اجازه‌ها ... ],
    Role.MANAGER: [ WORKER_READ, WORKER_CREATE, ..., ATTENDANCE_EXPORT, ... ],
    Role.OPERATOR: [ WORKER_READ, WORKER_CREATE, ATTENDANCE_READ, ... ],
    Role.VIEWER: [ WORKER_READ, ATTENDANCE_READ, API_ACCESS ],
}
```

مثلاً فقط **ADMIN** می‌تواند کارمند حذف کند؛ **VIEWER** فقط می‌تواند ببیند. رمزها هم به‌صورت **هش (Hash)** ذخیره می‌شوند نه متن ساده — [auth.py](file:///s:/TRAE/CV_Attendance/auth.py#L17) با `sha256_crypt`. زیرساخت JWT/RBAC کار امیرمحمد است.

### ۹٫۱. ارزیابی کیفیت — [quality.py](file:///s:/TRAE/CV_Attendance/cv_modules/quality.py)

- **Brightness (روشنایی):** میانگین روشنایی؛ بهترین حدود ۱۲۸ (نه خیلی تاریک، نه سوخته).

### ۹٫۲. تشخیص زنده‌بودن — [liveness.py](file:///s:/TRAE/CV_Attendance/cv_modules/liveness.py)
جلوی تقلب با عکس چاپی یا صفحه‌ی موبایل را می‌گیرد. سه نشانه بررسی می‌شود و ترکیب می‌شوند — [liveness.py](file:///s:/TRAE/CV_Attendance/cv_modules/liveness.py#L253-L263):

### ۹٫۳. ردیابی چهره — [tracking.py](file:///s:/TRAE/CV_Attendance/cv_modules/tracking.py)

- **رأی‌گیری هویت:** در چند فریم رأی جمع می‌شود؛ هویتی که بیشترین رأی وزن‌دار را دارد، هویت نهایی می‌شود — [tracking.py](file:///s:/TRAE/CV_Attendance/cv_modules/tracking.py#L118-L132). این کار «چشمک‌زدن» اسم روی صفحه را حذف می‌کند.

## ۱۱. نکات کلیدی برای اسلاید

از این‌ها می‌توانی مستقیم اسلاید بسازی. هر بولت یک اسلاید یا یک نکته‌ی گفتاری است.

### اسلاید ۱ — مسئله و راه‌حل
- مشکل: ثبت حضور دستی/کارتی کند و قابل تقلب است.
- راه‌حل: حضور خودکار با تشخیص چهره از دوربین زنده.

### اسلاید ۲ — ایده‌ی محوری
- «هر صورت → یک بردار ۵۱۲ عددی (امضای عددی)».
- «تشخیص چهره = مقایسه‌ی دو بردار».

### اسلاید ۳ — خط لوله (Pipeline)
- دوربین → آشکارسازی → کیفیت → بردار → مقایسه → زنده‌بودن → ردیابی → ثبت حضور.
- (همان نمودار بخش ۴ را کپی کن.)

### اسلاید ۴ — بردار چهره (عمیق)
- ابزار: InsightFace + ArcFace، بسته‌ی `buffalo_l`، اجرا روی CPU.
- مقایسه با **شباهت کسینوسی**؛ آستانه ۰٫۴ (یعنی `1 - tolerance`).
- ذخیره در جدول `face_encodings` به‌صورت JSON در SQLite.

### اسلاید ۵ — منطق حضور
- اولین دیده‌شدن = ورود، آخرین = خروج، ساعت کار = تفاضل آن‌ها.
- مهمان‌ها حضور کاذب نمی‌سازند.
- Cooldown برای جلوگیری از رکورد تکراری.

### اسلاید ۶ — ماژول‌های بینایی
- کیفیت (تاری/نور/زاویه)، زنده‌بودن (پلک/بافت/حرکت)، ردیابی (IoU + کالمن).

### اسلاید ۷ — وب و امنیت
- FastAPI + Thread Pool (پاسخ ۵۵–۸۹ms)، MJPEG، WebSocket.
- امنیت: JWT + RBAC، رمز هش‌شده، پنل ادمین.

### اسلاید ۸ — چالش‌های فنی و رفع آن‌ها (نقطه‌قوت ارائه)
- باگ SCRFD broadcast → اصلاح `det_size=(320,320)`.
- جداسازی فریم خام از نمایشی برای بردار سالم.
- مهاجرت ۱۲۸→۵۱۲ بُعدی با پشتیبان‌گیری و بازسازی بردارها.
- رفع کندی Event Loop با Thread Pool.

### چند سوال محتمل داور و پاسخ کوتاه
- **چرا کسینوسی نه اقلیدسی؟** چون ArcFace طوری آموزش دیده که هویت در «جهت» بردار کدگذاری می‌شود، نه طولش؛ کسینوسی جهت را می‌سنجد.
- **چرا ۵۱۲ بُعد بهتر از ۱۲۸؟** توصیف دقیق‌تر و تفکیک‌پذیری بالاتر بین افراد.
- **اگر دو نفر شبیه باشند؟** سیستم با «margin» (فاصله‌ی نفر اول و دوم) اطمینان را کم می‌کند.
- **اگر کسی عکس نشان دهد؟** ماژول Liveness (بافت/پلک/حرکت) آن را رد می‌کند.
- **اگر InsightFace نصب نشود؟** سیستم خودکار به dlib (۱۲۸ بُعدی) برمی‌گردد.
- **حریم خصوصی؟** فقط بردار عددی ذخیره می‌شود؛ با حذف کارمند، بردار و عکس‌هایش هم حذف می‌شوند.
